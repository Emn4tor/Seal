# Seal — what's still missing

Audit of gaps in the app, verified against the actual code (not just claims — the headline finding was independently confirmed by reading the relevant source directly). `docs/THREAT_MODEL.md` already documents several known limitations (no multi-device support, Olm/Megolm session state not persisted across restart, presence is single-shot not a heartbeat, voice isn't additionally E2E-wrapped beyond Noise transport, voice is full-mesh with no size cap, voice-channel presence is group-visible, voice changer isn't a real anonymity guarantee) — those are **not** repeated below; everything here is *additional* to that list.

## Critical — undermines the core premise

- [x] ~~Two instances on the same LAN can't connect to each other~~ Fixed: `crates/core/src/service.rs` now binds `0.0.0.0` instead of loopback and advertises every non-loopback listen address (via the new `ChatNode::wait_for_listen_addrs`) through presence, so two machines on the same network can dial each other directly.
- [ ] **Two instances on *different* networks (behind different NATs/routers) still can't connect.** The relay/autonat/dcutr behaviours are already fully wired into the swarm (`crates/net/src/behaviour.rs:22-23,26`), but there's no relay *server* anywhere for a peer behind a NAT to bounce through — `relay_addrs` sent to the directory is still hardcoded `vec![]` (`service.rs`), and no relay/dcutr path is exercised by any test. This needs a publicly-reachable relay server (could run alongside wherever `directory-server` is deployed via `scripts/setup-backend.sh`, e.g. `seal.emn4tor.de` once it's live) plus the client-side wiring to reserve a circuit, advertise it, and let `dcutr` attempt to upgrade to a direct connection. Substantial, multi-file networking work with a real deployment decision attached; deserves its own dedicated plan. QUIC is also configured (`crates/net/src/swarm.rs`) but never actually bound — separate follow-up, noted in the code as needing its own look.
- [ ] **Offline-message retry is claimed but not implemented.** The README says "If the recipient is offline, the message waits locally and retries." `crates/storage/src/schema.sql:84-94` defines an `outbox` table for exactly this, but it's never read or written anywhere. `crates/core/src/node.rs:209-232` (`send_envelope`) always returns `Ok(())` regardless of delivery outcome, and the response/ACK and failure variants of the request-response protocol are silently discarded (`node.rs:355-384`). No retry, no UI feedback on failure. Deliberately not bundled into the group-removal/contact-removal work below — retry/backoff policy and how the UI should reflect "pending vs. failed" deserves its own focused design.
- [x] ~~Removing a group member doesn't rotate the key client-side~~ `crates/core/src/service.rs` now has `remove_member_from_group` (kicks + rotates the acting member's own outbound session, re-sharing with everyone left) and `leave_group` (self-removal), wired end-to-end through `commands.rs`/`actor.rs`/`tauri.ts` to real UI in `MemberList.tsx` (owner-only "Remove") and `ConversationList.tsx` ("Leave group"). **Important remaining caveat**, verified by reading `crypto-session/tests/megolm.rs::removed_member_cannot_decrypt_messages_sent_after_rotation`: `rotate_group_key` only ever rotates *the calling member's own* session — it can't make *other* remaining members rotate theirs too. So a kick now genuinely protects the acting member's (typically the owner's) future messages, but doesn't yet guarantee a removed member can never decrypt *any* remaining member's future message. That needs a broader "all members rotate on roster change" mechanism — real additional scope, not done here, and the README's claim is still only partially true until it is.

## Significant — features half-built, wiring gap not a design gap

- [x] ~~Presence heartbeat exists, tested, and unused~~ Fixed: `crates/net/src/presence.rs::run_presence_heartbeat_loop` is now spawned from `AppService::load_or_create` (`crates/core/src/service.rs`) on a 150s interval, using a second `Identity` built from the same pickle and a `HeartbeatGuard` (`Drop` → `.abort()`) tied to `AppService`'s own lifetime so switching accounts can't leak a stale heartbeat. Re-announces the same addresses captured at startup rather than re-querying the live swarm each tick (architectural constraint — `AppService` is single-actor-owned, see `actor.rs`) — a real improvement over no heartbeat at all, but not full dynamic re-discovery.
- [ ] **A "verified contact" badge that can never be true.** `contacts.verified` is always inserted `0` and never updated anywhere, yet `ConversationList.tsx:183` renders a verified badge driven by this column — dead UI for an unfinished safety-number-verification feature. Explicitly left alone (confirmed, not an oversight) as a placeholder for a possible future verification feature.
- [x] ~~`contacts.last_seen_at` is dead schema~~ Fixed: `contacts_store::upsert_contact` now takes and stores it, updated on every successful directory sync (`service.rs::add_contact_by_user_id`).
- [ ] **`messages.delivered` is still hardcoded `true`** — no real delivery-status tracking. Coupled to the offline-retry item above (same deferral reasoning).
- [x] ~~**Message send failures were silent and lost your draft.**~~ Fixed: `ChatPane.tsx` now restores the draft/attachment and shows an inline error on send failure; `App.tsx`'s message-history load and `SettingsPanel.tsx`'s purge/remove-account/save-server actions now surface errors instead of failing silently.
- [ ] **Messaging feature set is absent full-stack, not just missing UI**: no edit/delete/unsend, no replies/threading, no reactions, no read receipts, no typing indicators, no message search, no link previews (message body is rendered as raw text, `ChatPane.tsx:190`), no per-message copy button. `MessageDto` doesn't even carry a `message_id`, so none of these can be bolted on client-side alone — needs a wire-protocol/schema change first, a real multi-session feature, not a fix.
- [x] ~~Contact/group management is read-only~~ **Partially fixed**: block/remove contact, leave-group, and kick-member all now exist end-to-end (backend + UI), matching the two items marked done above. Still not done: rename group/channel, group/channel icon or description, member-role change, contact search.
- [x] ~~Stale UI copy contradicts a working feature~~ Fixed: removed the "coming in a future update... no audio yet" paragraph from `CreateChannelModal.tsx` — voice is fully implemented.

## Platform / testing

- [x] ~~CI never builds or tests on Windows or Linux~~ Fixed: `.github/workflows/ci.yml`'s `rust` job is now a `[macos-latest, ubuntu-latest, windows-latest]` matrix (fmt/clippy/test on all three — `apps/desktop/src-tauri` is a workspace member, so this already exercises a real Tauri compile on each OS; `cargo-audit` only runs once, on ubuntu, since it's platform-independent). **Unverified**: this can only actually be confirmed once pushed and run by GitHub Actions, which wasn't done as part of this pass (not triggered without being asked).
- [x] ~~Zero frontend tests~~ **Partially fixed**: `vitest` + `@testing-library/react` + `jsdom` now set up (`apps/desktop/vitest.config.ts`, `npm run test`, wired into CI's `frontend` job), with one real regression test (`ChatPane.test.tsx`, covering the send-failure-restores-draft fix above). Broader component coverage is still future work. `crates/wire-proto` still has no tests despite containing the directory-auth request-signing logic everything else depends on.
- [ ] **Relay/dcutr NAT traversal is untested** (consistent with the connectivity finding above — nothing exercises it because nothing uses it yet).
- [x] ~~Two stray untracked experiment files on disk~~ Fixed: moved (not deleted — they were never committed, but deleting untracked work outright isn't reversible) into `.abandoned-experiments/` (gitignored). A third one turned up during cleanup that the original audit missed: `crates/directory-server/src/db 2.rs`, moved alongside the other two.

## Onboarding / transparency

- [x] ~~No warning about the backup/multi-device downside~~ Fixed: `Onboarding.tsx`, `TutorialWizard.tsx`, and `SettingsPanel.tsx`'s panic-purge section now all explicitly note there's no export/backup and no multi-device support, so losing the device means losing the identity for good.
- [ ] **No identity backup or export exists at all** — no recovery phrase, no key export command anywhere. The UI is now honest about this (see above), but the actual feature still doesn't exist. Security-critical, needs careful dedicated design (what does safely exporting a private key even look like in this UI?) — deliberately not rushed alongside everything else in this pass.

## Accessibility

- [x] ~~No modal closes on Escape~~ Fixed: `lib/useModalEscape.ts` (a small shared hook) is now used by all five modal-like overlays (`Modal.tsx`, `CreateChannelModal.tsx`, `TutorialWizard.tsx`, `SettingsPanel.tsx`, `ImageLightbox.tsx`).
- [ ] **Still no full focus trap** (Tab cycling within a dialog rather than escaping into the page behind it). Escape-to-close was judged the higher-value, lower-risk piece to do now; full focus-trapping is a further, separate follow-up if it turns out to matter in practice.

## Recommended server

- [x] `https://seal.emn4tor.de` is now baked in as the recommended/default directory server (via `SEAL_DEFAULT_DIRECTORY_URL`, set in all four `scripts/build-*` scripts) — shown as the "Seal" option in the first-run screen. "Custom server" and "Local test server" remain exactly as they were. Not yet verifiable end-to-end since the server isn't running yet.
